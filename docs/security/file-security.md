# File security

Status: file-handling specification. This document defines required controls.
It does not assert that the upload, inspection, storage, or download paths are
implemented or verified. Verification must be executed as described in section
12.

## 1. Principles

- A file is untrusted until it has passed inspection and has been explicitly
  approved.
- The declared filename and declared content type are untrusted metadata.
- Uploaded bytes are never executed by the API, the public site, or the asset
  origin.
- Storage names are generated by the server. User input never becomes a path
  component.
- Every download is authorized again at download time. Approval is not a public
  grant.
- The file inspection path is isolated from the request path.
- The asset origin is cookieless and separate from the application origins.
- Rejection is the default. A new file type requires a threat review and an
  update to this document.

## 2. Pipeline

```
Browser
   |
   | authenticated upload, one file, 25 MiB maximum
   v
API authorization
   |
   | stream, hash, generate identifier
   v
Quarantine storage (private, no public URL)
   |
   | inspection job
   v
Isolated inspection worker
   |
   +---- rejected ----> purge bytes, keep metadata for audit
   |
   v
Approved storage
   |
   | authorized download, short-lived access
   v
Cookieless asset origin
```

### 2.1 States

| State | Meaning | Allowed next states |
| --- | --- | --- |
| `quarantined` | Bytes stored, no inspection result | `scanning`, `deleted` |
| `scanning` | Inspection worker is processing | `approved`, `rejected`, `deleted` |
| `approved` | Inspection passed, bytes available for authorized download | `deleted` |
| `rejected` | Inspection failed or the file is not allowed | `deleted` |
| `deleted` | Metadata retained, bytes scheduled or completed for purge | None |

Rules:

- No transition to `approved` without a completed inspection result.
- No download is served while the state is `quarantined`, `scanning`, or
  `rejected`.
- A failed inspection job is retried a bounded number of times, then moves to
  `rejected`.
- State transitions are atomic and audited.
- A repeated inspection job is idempotent. It must not overwrite an `approved`
  result with a later failure without an explicit security decision.
- Deleting an approved file invalidates outstanding download access.

## 3. Allowed types

The initial allowlist is deliberately small. Anything not listed is rejected.

| Category | Canonical type | Extensions | Maximum size | Required handling |
| --- | --- | --- | --- | --- |
| Image | `image/png` | `.png` | 25 MiB | Decode, enforce pixel limits, re-encode, strip metadata |
| Image | `image/jpeg` | `.jpg`, `.jpeg` | 25 MiB | Decode, enforce pixel limits, re-encode, strip metadata |
| Image | `image/webp` | `.webp` | 25 MiB | Decode, enforce pixel limits, re-encode, strip metadata |
| Document | `application/pdf` | `.pdf` | 25 MiB | Reject active content, scan, serve as attachment |
| Text | `text/plain` | `.txt` | 25 MiB | Require valid UTF-8, reject NUL and disallowed control characters |
| Text | `text/markdown` | `.md` | 25 MiB | Require valid UTF-8, render with raw HTML disabled, serve source as attachment |
| Archive | `application/zip` | `.zip` | 25 MiB | Inspect central directory with limits, scan, no extraction in the API |

Explicitly rejected, even if a library can parse them:

- SVG (`image/svg+xml`) in every context, including avatars and logos.
- HTML, XHTML, XML with scripts, CSS, JavaScript, and web bundles.
- Executables, shared libraries, object files, installers, and disk images.
- Shell, batch, PowerShell, Python, Perl, PHP, and other scripts.
- Office documents with macros or embedded objects. OOXML is not in the initial
  allowlist.
- Encrypted or password-protected archives.
- Spanned or multi-disk archives.
- Files whose detected type differs from the declared type.
- Files that contain another archive or executable as an entry.

The 25 MiB limit applies to the file and to the upload request. A lower limit
may be configured for a specific purpose, but no path may accept more than
25 MiB without a reviewed policy change.

## 4. Upload path

1. Authenticate the request and establish the organization context.
2. Authorize the upload against the target resource: project, submission,
   organization profile, or another explicitly supported owner.
3. Apply per-user and per-organization upload rate limits and storage quotas.
4. Enforce the request body limit and the 25 MiB file limit. Count actual bytes
   while streaming; do not trust `Content-Length` alone.
5. Reject a declared type that is not in the allowlist before accepting the
   body.
6. Stream the body to a quarantine location. Do not buffer the whole file in
   memory.
7. Compute SHA-256 while streaming.
8. Generate a file identifier. Never use the user's filename as part of the
   storage key.
9. Record metadata: organization, owning resource, uploader, original filename,
   declared type, detected type placeholder, byte size, checksum, status
   `quarantined`, and timestamps.
10. Enqueue an inspection job with the file identifier and organization
    identifier.
11. Return a pending representation. Do not return a download URL before
    approval.

Upload rules:

- One file per request in the initial implementation. If batch upload is added,
  the total request size remains bounded and every file is inspected
  independently.
- Reject an unsupported `Content-Type` even if the bytes look allowed. The
  declared type is a hint, not a grant.
- Limit the original filename to 255 bytes. Strip path separators and control
  characters for display. Store the original only as metadata.
- Reject filenames containing NUL, CR, LF, path separators, or traversal
  sequences. The storage key does not use the filename regardless.
- Do not trust client-provided checksums, dimensions, page counts, or archive
  entry counts.
- A failed metadata insert after bytes are written must clean up the
  quarantine object.
- Upload endpoints are rate-limited and have a bounded request timeout.
- The API never writes to the approved storage prefix.

## 5. Magic-byte and content validation

Validate the bytes, not the extension.

| Type | Check |
| --- | --- |
| PNG | First eight bytes are `89 50 4E 47 0D 0A 1A 0A`; parse the chunk structure; reject malformed or truncated files |
| JPEG | Starts with `FF D8 FF`; parse markers; reject malformed or truncated files |
| WebP | `RIFF` at offset 0 and `WEBP` at offset 8; validate the container and chunks |
| PDF | Starts with `%PDF-`; parse the document structure; inspect for active content |
| ZIP | Starts with `PK 03 04`, `PK 05 06`, or `PK 07 08`; parse the central directory; reject spanned archives |
| Text | Strict UTF-8 decoding; reject NUL, invalid sequences, and disallowed control characters |

Rules:

- Compare detected type with the declared type and the extension. A mismatch is
  rejection, not a warning.
- Use a maintained parser or file-type library. Do not implement container
  parsing from scratch.
- Run parsing in the inspection worker, not in the API request path.
- Reject a file when the parser cannot confidently identify it.
- Do not rely on a single magic byte sequence. A polyglot can satisfy more than
  one format. The allowlist and the parser must agree.

## 6. Image handling

- Decode the image in the inspection worker with explicit width, height, and
  pixel limits. Reject an image that exceeds the limits before full
  decompression when the format permits.
- Initial limits: maximum 12,000 pixels on either axis and maximum 50 million
  pixels total.
- Re-encode the image to the canonical output type. Re-encoding removes EXIF,
  ICC profiles that are not required, comments, trailing data, and format
  quirks that can carry active content.
- Strip animation unless the product explicitly supports it. Animated images
  multiply decode cost and can carry unexpected frames.
- Do not process SVG. Do not pass uploaded images through the Next.js image
  optimizer. Disable SVG optimization for untrusted content.
- Store only the re-encoded bytes in approved storage. The original upload is
  purged after approval or rejection according to retention policy.
- Recompute the checksum after re-encoding. The approved checksum is the one
  served and audited.

## 7. PDF handling

PDF is allowed only as a document attachment. It is never rendered inline by
default.

The inspector must reject:

- Encryption or password protection.
- JavaScript, including names such as `/JavaScript` and `/JS`.
- Launch actions and automatic actions.
- Embedded files and rich media.
- Open actions that execute script.
- Malformed cross-reference tables, object streams, or trailer structures that
  the parser cannot validate.
- Files that exceed parser object, stream, or page limits.

If the parser cannot prove the absence of active content, the file is rejected.
Scanning alone is not sufficient for active content. The download is served
with `Content-Disposition: attachment` and a sandboxing CSP.

## 8. Archive handling

ZIP is allowed only for project attachments and only after central-directory
inspection. The API never extracts an archive. The inspection worker may stream
entries inside its sandbox.

Limits:

| Limit | Value |
| --- | --- |
| Maximum entries | 500 |
| Maximum total uncompressed size | 100 MiB |
| Maximum uncompressed size per entry | 25 MiB |
| Maximum compression ratio per entry | 100:1 |
| Maximum path length | 255 bytes |
| Maximum nested archive depth | 0 (nested archives rejected) |
| Maximum archive size | 25 MiB |

Reject an archive when any of the following is true:

- An entry name is absolute, contains a `..` segment, contains a backslash, a
  drive letter, a NUL, or a control character.
- An entry is a symbolic link, hard link, device, or other non-regular file.
- The archive is encrypted or password-protected.
- The archive is spanned or multi-disk.
- Two entries normalize to the same path.
- An entry is itself an archive, executable, HTML, SVG, or other disallowed
  content.
- The advertised sizes are inconsistent with the actual streamed bytes.
- The total uncompressed size or ratio exceeds the limits.
- The parser reports an overlapping-entry or offset anomaly it cannot resolve
  safely.

Do not trust the central-directory sizes alone. Count actual bytes while
reading and stop at the limit. A zip bomb can lie about its uncompressed size.
Use a parser that supports bounded streaming and reject ZIP64 values that exceed
the limits.

## 9. Inspection worker

The inspection worker is a separate process from the API request path.

Requirements:

- Run as a non-root user.
- Use a read-only root filesystem and a bounded temporary directory.
- Apply CPU, memory, process, file-descriptor, and wall-clock limits. Initial
  limits: 1 CPU, 512 MiB memory, 120 seconds, and 256 MiB temporary storage.
- Have no inbound network access.
- Have no outbound network access.
- Use a seccomp profile or equivalent system-call restriction where the platform
  supports it.
- Never invoke a shell, `child_process`, or an external converter with uploaded
  content.
- Use maintained libraries for parsing, decoding, and scanning.
- Keep malware signatures current. If the scanner is unavailable or its
  signatures are stale, fail closed: hold or reject the file, never approve it.
- Record a scan result with scanner name, signature version, timestamp, and
  outcome.
- Kill the process and reject the file when a limit is exceeded.
- Purge temporary files at the end of the job, including on failure.

The worker may share the application codebase, but it runs as a separate
process with a separate resource profile and no request-serving authority.

## 10. Storage

### 10.1 Generated names

Approved storage keys use generated identifiers only:

```text
quarantine/<organization-id>/<file-id>
approved/<organization-id>/<file-id>.<canonical-extension>
```

Rules:

- `<file-id>` is a server-generated UUID or equivalent random identifier.
- `<canonical-extension>` is derived from the validated type, not from the
  user's filename.
- The original filename is stored only in metadata.
- No user input is concatenated into a filesystem path or object key.
- If a future feature needs a user-visible path, it must be mapped through a
  database lookup, not used as a storage key.

### 10.2 Storage controls

- Quarantine and approved storage are private. There is no public bucket,
  public object ACL, or directory listing.
- Encryption at rest is required.
- Access credentials are separate from the API database credentials and are
  least-privilege for the required prefixes.
- The asset origin can read only approved storage. It cannot read quarantine.
- Object versioning and lifecycle rules support recovery and purge.
- Checksums are stored and verified when serving.
- Do not deduplicate files across organizations. A per-organization checksum
  index is permitted only if it cannot reveal another organization's file.
- Deletion is a soft delete followed by a bounded purge job. Outstanding signed
  access expires before or at purge.
- Orphaned quarantine objects are deleted by a scheduled job.

## 11. Download path

### 11.1 Authorization

Every download performs the six-step authorization check against the file's
owning resource. Approval is not a public grant.

- Verify identity and session.
- Verify the organization context.
- Load the file with its organization and owning resource.
- Verify active membership.
- Verify the download permission for the resource.
- Verify competition eligibility, assignment, or ownership where applicable.
- Require status `approved`.
- Deny quarantined, scanning, rejected, and deleted files.
- Deny cross-organization access with a not-found response where appropriate.

The download either returns a short-lived signed asset URL or streams the bytes
through the API. The preferred design is a signed URL to the cookieless asset
origin.

### 11.2 Asset origin

- Use a separate hostname, for example `assets.nethack.example`.
- The asset origin sets no cookies and accepts no session cookie.
- It has no CORS credentials and no wildcard credentialed CORS.
- It serves approved bytes only. No directory listing, no upload, no dynamic
  code, and no execution.
- Signed access is bound to one file, one organization, and a short expiry.
  Initial expiry: 60 seconds.
- The signing key is server-side and rotated.
- A signed URL is not reused across files or organizations.
- The asset origin does not run the Next.js image optimizer or any converter on
  request.
- TLS and HSTS apply.

### 11.3 Response headers

| Header | Required value |
| --- | --- |
| `Content-Type` | Canonical validated type from the server, never the uploaded header |
| `Content-Length` | Exact approved byte length |
| `Content-Disposition` | `attachment` by default; safe ASCII fallback plus `filename*` UTF-8 encoding; no CR or LF |
| `X-Content-Type-Options` | `nosniff` |
| `Content-Security-Policy` | `default-src 'none'; sandbox` on the asset response |
| `Cross-Origin-Resource-Policy` | `same-site` for private files; `cross-origin` only for explicitly public showcase assets |
| `Referrer-Policy` | `no-referrer` |
| `Cache-Control` | `private, no-store` for private files; immutable public caching only for published assets with a content hash |
| `X-Download-Options` | `noopen` |
| `Accept-Ranges` | `none` for private sensitive files; bounded ranges only where explicitly supported |
| `Set-Cookie` | Must not be present on the asset origin |

Additional rules:

- A safe inline image policy may be approved only for re-encoded PNG, JPEG, or
  WebP images. PDF, ZIP, text, and Markdown are always attachments.
- Sanitize the download filename for display. Remove path separators, control
  characters, and header-injection characters. Encode UTF-8 filenames with
  RFC 5987/6266.
- Do not compress already compressed content on the fly.
- Do not expose internal storage paths, bucket names, or object keys in
  headers or error responses.
- A missing or expired signature returns `403` or `404` without revealing
  whether the file exists.

## 12. Testing

### 12.1 Upload and type tests

- Every allowed type uploads and reaches `approved`.
- Every disallowed type is rejected with a stable, non-sensitive error.
- A declared type that does not match the magic bytes is rejected.
- A polyglot file is rejected.
- An executable, script, HTML, SVG, or encrypted archive is rejected.
- A PDF with JavaScript, launch action, embedded file, or encryption is
  rejected.
- A text file with invalid UTF-8 or NUL is rejected.
- An image that exceeds pixel or dimension limits is rejected.
- A file over 25 MiB is rejected with `413`.
- A chunked upload that exceeds the limit is rejected while streaming.

### 12.2 Path and storage tests

- A filename containing `../`, an absolute path, a backslash, a drive letter, a
  NUL, or a control character cannot influence the storage key.
- The stored key contains only the organization identifier, generated file
  identifier, and canonical extension.
- A file cannot be downloaded before approval.
- A rejected file cannot be downloaded.
- A deleted file cannot be downloaded.
- A cross-organization file identifier is denied.
- A signed URL is bound to one file and expires.
- The asset origin does not set cookies and does not accept them for
  authorization.

### 12.3 Archive tests

- `../` entry, absolute entry, backslash entry, and drive-letter entry are
  rejected.
- Symbolic link, hard link, encrypted, spanned, and nested archives are
  rejected.
- Entry count, total size, per-entry size, ratio, and path length limits are
  enforced.
- A lying central directory cannot exceed the actual streamed byte limits.
- Duplicate normalized entry names are rejected.
- The API never extracts an archive.

### 12.4 Worker and execution tests

- The worker cannot reach the network.
- The worker cannot write outside its temporary directory.
- CPU, memory, time, and process limits are enforced.
- A scanner failure does not approve a file.
- A parser timeout or crash rejects the file and cleans up.
- No `child_process`, shell, dynamic import, or template rendering is invoked
  with uploaded content.
- The API never serves a file from its own filesystem.

### 12.5 Download tests

- `Content-Type` is server-derived.
- `Content-Disposition` is attachment for PDF, ZIP, text, and Markdown.
- `nosniff`, sandbox CSP, `no-referrer`, and cache headers are present.
- No cookie is set by the asset origin.
- The signed URL expires and cannot be replayed after expiry.
- A public showcase asset uses a deliberate public cache policy only after
  publication.
- A private asset is not cached by a shared cache.

### 12.6 Fuzzing and independent review

- Fuzz image, PDF, and ZIP parsers with malformed and truncated inputs.
- Fuzz the upload metadata and filename handling.
- Include malicious-file review in the pre-launch penetration test.
- Re-run the file suite after any parser, scanner, or storage dependency update.

## 13. Incident handling

When inspection detects malware or a forbidden active file:

1. Keep the file in quarantine. Do not approve it.
2. Record the signature, checksum, uploader, organization, and owning resource.
3. Block the checksum for the organization or platform as appropriate.
4. Identify whether the file was ever downloaded. If it was, treat the download
   as a potential exposure and follow `docs/security/incident-response.md`.
5. Preserve evidence before purging bytes. Store evidence outside the public
   application path.
6. Purge the quarantined bytes after evidence capture.
7. Notify the uploader with a generic rejection. Keep scanner details in the
   private security log.
8. Update signatures and tests, and review whether the allowlist or limits must
   change.

If an approved file is later found to be malicious, revoke outstanding signed
URLs, remove it from approved storage, preserve evidence, notify affected
organizations and users as required, and add a regression test.
